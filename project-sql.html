Project Overview

What This Project Demonstrates

The Task

Design a complete relational database for a Nigerian retail business from scratch — covering customers, suppliers, products, orders, order details, and payments.

Then write SQL queries that answer the kind of questions a real business manager would ask: Who are our most loyal customers? Which products are slow-moving? Which suppliers sell the most? What is total revenue?

The goal was to build something that could actually be used — not just a practice exercise.

What I Built

I created a 6-table relational database with proper primary keys, foreign keys, and referential integrity constraints — ensuring data consistency across every table.

I then populated the database with realistic Nigerian retail data: 20 customers across Lagos, Abuja, Ibadan, and Enugu; 10 real Nigerian suppliers (Dangote, Nestle, Coca-Cola, MTN etc.); 30 products; 40 orders; and 40 payments.

Finally, I wrote 15+ SQL queries covering basic reporting, multi-table JOINs, aggregations, HAVING clauses, subqueries, and window functions.

Skills Demonstrated

Database design: Creating tables with appropriate data types, primary keys, foreign keys, and NOT NULL constraints.

Data manipulation: ALTER TABLE, INSERT statements, handling UNIQUE constraints.

Business queries: Multi-table JOINs across 5 tables in a single query, GROUP BY with HAVING, ORDER BY, and LIMIT.

Advanced SQL: Window functions (RANK OVER), correlated subqueries, date formatting with DATE_FORMAT.

Business Intelligence Queries

These are the actual queries I wrote — each one answers a real business question. The queries are grouped from basic to advanced.

Full Customer Purchase Report 5-table JOIN
Joins 5 tables to show every customer's full purchase history — name, order date, product, quantity, and amount paid in one query. This is the kind of report a sales manager needs every month.
SELECT c.first_name, c.last_name,
       o.order_date, p.product_name,
       od.quantity, pay.amount AS amount_paid
FROM customers c
JOIN orders o
  ON c.customer_ID = o.customer_ID
JOIN order_details od
  ON od.order_ID = o.order_ID
JOIN product p
  ON od.product_ID = p.product_ID
JOIN payments pay
  ON o.order_ID = pay.order_ID;
Business Summary Dashboard Subqueries
Returns total customers, total products, total orders, and total revenue in a single row — the kind of KPI summary an executive dashboard displays at the top of a report.
SELECT
  (SELECT COUNT(customer_ID) FROM customers)
    AS total_customers,
  (SELECT COUNT(product_ID) FROM product)
    AS total_products,
  (SELECT COUNT(order_ID) FROM orders)
    AS total_orders,
  (SELECT SUM(amount) FROM payments)
    AS total_revenue;
Customer Spending Rankings Window Function · RANK()
Ranks all customers by total spending using a SQL window function — identifying top spenders without removing any customers from the result. The RANK() OVER pattern is an advanced SQL skill.
SELECT c.customer_ID,
       c.first_name, c.last_name,
       SUM(p.amount) AS total_spent,
       RANK() OVER (
         ORDER BY SUM(p.amount) DESC
       ) AS spending_rank
FROM customers c
LEFT JOIN orders o
  ON c.customer_ID = o.customer_ID
LEFT JOIN payments p
  ON p.order_ID = o.order_ID
GROUP BY c.customer_ID,
         c.first_name, c.last_name;
Highest-Revenue Product Category GROUP BY · ORDER BY
Finds which product category (Food, Beverages, Personal Care, Telecom, Building) generates the most revenue — helping management decide where to focus stock and promotions.
SELECT p.category,
       SUM(pay.amount) AS total_revenue
FROM product p
JOIN order_details od
  ON p.product_ID = od.product_ID
JOIN payments pay
  ON od.order_ID = pay.order_ID
GROUP BY p.category
ORDER BY SUM(pay.amount) DESC
LIMIT 1;
Slow-Moving Products LEFT JOIN · Business Intelligence
Identifies the lowest-performing products by total sales revenue. A left join ensures products with zero sales still appear in the results — so nothing is hidden from management.
SELECT p.product_ID,
       p.product_name,
       SUM(pay.amount) AS total_sales
FROM product p
LEFT JOIN order_details od
  ON od.product_ID = p.product_ID
LEFT JOIN payments pay
  ON pay.order_ID = od.order_ID
GROUP BY p.product_ID, p.product_name
ORDER BY SUM(pay.amount) ASC;
Monthly Sales Performance DATE_FORMAT · Time Series
Groups total sales by month using DATE_FORMAT — producing a month-by-month revenue trend that can be used to identify peak periods and seasonal patterns.
SELECT
  DATE_FORMAT(payment_date, "%b") AS month,
  SUM(amount) AS total_sales
FROM payments
GROUP BY DATE_FORMAT(payment_date, "%b")
ORDER BY MIN(payment_date);
Products Never Sold LEFT JOIN · NULL Check
Finds products that exist in the catalogue but have never appeared in any order — using a left join and WHERE NULL check. Useful for identifying dead stock that should be discontinued.
SELECT p.product_ID, p.product_name
FROM product p
LEFT JOIN order_details od
  ON p.product_ID = od.product_ID
WHERE od.product_ID IS NULL;
Products Above Average Price Correlated Subquery
Returns all products priced above the dataset average — using a subquery inside a WHERE clause. This is a common pattern for filtering based on calculated thresholds.
SELECT product_ID, product_name, price
FROM product
WHERE price > (
  SELECT AVG(price) FROM product
)
ORDER BY price DESC;

What I Learned
🗄️ Database Design Matters
Getting the schema right before writing a single query saves enormous time. A well-structured database makes every query cleaner and faster to write.
🔗 JOINs Are Everything
Most real business questions require data from multiple tables. Mastering LEFT JOIN vs INNER JOIN determines whether missing data disappears or stays visible in your results.
📊 Think in Business Questions
The best SQL queries start with a business question, not a syntax idea. "Who are our most loyal customers?" leads to better code than "let me use GROUP BY".
🪟 Window Functions Are Powerful
RANK() OVER lets you rank and compare rows without collapsing your result set — something GROUP BY alone can't do. This opens up a whole category of business analysis.
